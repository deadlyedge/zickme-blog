# `documents/old-plans` 开发路线总结与经验提炼

> 本文基于 `documents/old-plans` 中的阶段计划、阶段总结、架构审计和代码清理方案整理。  
> 这些文档记录了项目从一个个人博客逐步演化为“博客 + Gallery + 数据库副本 + Cloudinary + Dashboard + 同步平台”，随后又主动进行架构减法、回归 Git-first 单向发布的过程。
>
> 由于旧文档中存在“计划目标”“阶段总结”“审计结论”和“后续修正”之间的差异，本文更关注路线演进和经验，而不把每份文档中的“已完成”都视为最终事实。

---

## 一、路线总览：从功能扩张到架构收敛

整个开发过程大致经历了以下几个大阶段：

```text
基础架构重建
    ↓
产品体验与用户系统完善
    ↓
代码质量与安全治理
    ↓
独立 Gallery 内容体系
    ↓
Post/Gallery 同步平台化
    ↓
内容生产闭环与数据库快照
    ↓
架构减法：回归 Git-first 单向发布
```

这条路线最值得注意的地方是：

> 项目并不是一开始就朝着复杂同步平台设计，而是在不断解决实际问题的过程中，逐步引入了双向同步、冲突处理、运行记录、快照和 Dashboard 管理能力。  
> 直到 Stage 9 之后，才重新审视这些能力对于个人博客是否真的值得长期维护。

因此，这次开发路线本身可以看成一个完整的架构实验：

1. 先通过功能扩展验证需求；
2. 再通过平台化解决复杂性；
3. 最后通过架构审计识别过度设计；
4. 将系统重新收敛到更适合个人项目的模型。

---

# 二、大阶段一：基础架构统一与系统能力重建

## 1. 阶段目标

早期开发主要解决项目基础架构不统一的问题：

- 从 `blogs` / `projects` 双轨内容模型统一到 `Post`；
- 从 Prisma 迁移到 Drizzle ORM；
- 建立 PostgreSQL/Neon 数据访问层；
- 完善 Better Auth、Session 和角色权限；
- 建立 Dashboard 基础能力；
- 用 CLI 解决管理员密码重置问题；
- 逐步将博客从简单的 Markdown 展示站扩展为可管理的应用。

## 2. 主要成果

这一阶段完成了几个重要的基础决策：

### 内容模型统一

原本文章和项目分别处理，导致：

- 路由不同；
- 数据字段不同；
- 前端组件存在分支；
- 查询逻辑重复；
- 后续扩展成本较高。

最终统一为 `Post`，使用 tags、category 和 metadata 表达不同内容特征。这是一个正确的抽象收敛。

### ORM 和数据库现代化

从 Prisma 切换到 Drizzle，带来了：

- 更轻量的运行时依赖；
- 更直接的 SQL/schema 控制；
- 更适合 Serverless/Neon 的数据访问方式；
- 更明确的 migration 和 schema 管理。

但后续经验也表明，ORM 迁移本身只是基础设施工作，并不会自动解决业务边界问题。

### 权限和运维基础

项目没有引入邮件服务，而是选择：

- 管理员通过 CLI 重置密码；
- 普通用户由管理员在后台手动处理；
- Server Actions 统一进行 Session 和 Role 校验。

这说明对于个人项目，运维流程不必照搬 SaaS 产品的完整机制。低频操作可以使用受控 CLI 解决，不必为了“功能完整”引入邮件、任务队列等新系统。

## 3. 这一阶段的经验

### 经验一：先统一领域模型，再扩展功能

如果早期继续同时维护 `Blog`、`Project`、`Post` 三套概念，后续所有功能都会重复实现。

通用原则：

```text
先确认核心实体和边界
再设计页面、查询、权限和同步
```

### 经验二：基础设施升级要与实际收益绑定

Prisma → Drizzle 是有明确收益的基础设施迁移，但不应因为换了 ORM 就顺势引入大量不必要的业务平台能力。

未来项目中应区分：

- 必要的基础设施升级；
- 由升级顺带产生的“可以做”功能；
- 真正有用户价值的功能。

### 经验三：个人项目要优先解决高频运维问题

密码重置、权限校验、数据库初始化等问题虽然不显眼，但比复杂的内容编辑器更值得优先解决。低频运维功能可以保持简单、明确、可审计。

# 三、大阶段二：用户体验、视觉系统和互动能力建设

## 1. 阶段目标

在基础架构完成后，项目进入产品体验建设阶段，重点包括：

- 动态主题和站点配置；
- Landing Page 模块化；
- About 页面重构；
- 普通用户中心；
- 登录、登出和导航体验；
- 评论系统；
- 头像和隐私；
- 阅读体验；
- 响应式和移动端适配。

## 2. 主要成果

### 前台产品体验

逐步加入：

- 首页模块化配置；
- TOP 热门文章展示；
- 动态主题；
- About 时间线、技能和项目展示；
- 文章目录 TOC；
- 阅读进度；
- 阅读时间和字数；
- 代码复制；
- 外链展示；
- 移动端适配；
- 用户菜单和统一注销流程。

### 用户隐私和评论体验

Stage 5.1 是这一阶段中较成熟的一次治理：

- 公开评论不再返回完整邮箱；
- 内部 User 类型和公开评论 DTO 分离；
- 头像初始化只执行一次；
- Dicebear 使用稳定 seed；
- 禁止用户提交任意外链头像；
- Gravatar 作为用户主动选择的头像来源；
- 评论区用户入口统一指向 `/user`；
- Dashboard 增加返回博客入口。

这些修改说明一个重要原则：

> 隐私问题不能只在 UI 层隐藏，必须在服务端查询和 DTO 层解决。

例如，不在组件中渲染 `email` 并不等于安全；如果 Server Action 已经把邮箱返回给浏览器，隐私就已经泄露。

## 3. 这一阶段的经验

### 经验四：产品体验优化应该建立在稳定的数据契约上

评论头像、用户名称、Dashboard 菜单等功能看似是 UI 工作，实际上涉及：

- 公共 DTO；
- 权限边界；
- 认证状态；
- 数据隐私；
- 服务端和客户端的数据流。

因此，复杂交互最好先定义数据契约，再设计界面。

### 经验五：隐私保护要遵循“最小返回”原则

未来项目可以直接采用以下规则：

```text
内部数据库模型 ≠ 公开 API 模型 ≠ 管理后台模型
```

不同场景显式选择字段，而不是直接返回整个 ORM 查询对象。

### 经验六：视觉功能要设置明确边界

这一阶段曾经规划了动态 CSS、动态主题、自定义视觉效果等能力。经验是：

- 主题配置最好使用结构化字段；
- 不要默认允许任意 CSS；
- 外部 HTML、Markdown、图片 URL 都要有明确的安全策略；
- 视觉功能不应绕过内容和权限边界。

# 四、大阶段三：代码质量、安全和工程可靠性治理

## 1. 阶段目标

Stage 5.2 和 5.2.1 开始从“继续做功能”转向“先补质量基础”，重点包括：

- Server Action 输入校验；
- 权限边界统一；
- Markdown XSS 防护；
- 动态 CSS 安全；
- ZIP 和文件上传安全；
- TypeScript 类型收紧；
- Biome 规则收紧；
- 日志和错误统一；
- 测试框架和 CI 门禁；
- 历史代码和文档治理。

## 2. 识别出的主要问题

这一阶段的审计发现，项目虽然能够：

- 通过 TypeScript；
- 通过 lint；
- 成功构建；
- 正常运行；

但仍可能存在：

- `dangerouslySetInnerHTML` 带来的 Markdown XSS 风险；
- 动态 CSS 注入风险；
- ZIP Bomb 和路径穿越风险；
- `any` 和类型断言逃逸；
- Server Actions 输入验证不一致；
- 错误信息直接暴露内部实现；
- 自动化测试不足；
- CI 尚未形成真正的质量门禁。

后续还专门制定了从 `marked + dangerouslySetInnerHTML` 迁移到 `react-markdown`、`remark-gfm` 和可选 `rehype-sanitize` 的方案。

## 3. 这一阶段的经验

### 经验七：构建通过不等于系统安全

以下命令通过，只能说明有限范围内的问题不存在：

```bash
bun run lint
bunx tsc --noEmit
bun run build
```

它们无法证明：

- 权限一定正确；
- XSS 一定被阻止；
- dry-run 一定没有副作用；
- 快照恢复一定安全；
- 并发锁一定没有竞态；
- ZIP 上传一定不会越界。

因此，后续项目应尽早建立针对业务边界的测试，而不是等到系统复杂后再补。

### 经验八：安全检查应该前置到数据入口

推荐的 Server Action 顺序应始终是：

```text
解析输入
  ↓
Session 校验
  ↓
Role 校验
  ↓
资源权限校验
  ↓
业务逻辑
  ↓
安全 DTO
  ↓
日志和 revalidate
```

不要先执行数据库查询，再在页面上判断用户是否有权限。

### 经验九：测试优先覆盖“失败和危险路径”

个人项目不一定需要很大的 E2E 测试体系，但至少应优先覆盖：

- 未登录访问；
- 普通用户访问管理员 Action；
- 非法路径；
- 超大文件；
- XSS 输入；
- dry-run；
- 并发锁；
- 快照恢复失败；
- 版本冲突；
- Cloudinary 上传失败。

这些测试的价值通常高于大量普通成功路径测试。

# 五、大阶段四：独立 Gallery 内容体系建设

## 1. 为什么要从 Post 中拆出 Gallery

Stage 5 原本考虑过给 Post 增加“纯图片/相册布局”，但很快发现 Gallery 与普通文章在多个方面都不同：

| 维度 | Post | Gallery |
|---|---|---|
| 人工源 | Markdown | `album.yaml` + WebP |
| 内容组织 | 文章正文 | 相册和图片集合 |
| 媒体流程 | 文章图片 | 原始图片转 WebP |
| 前台交互 | 阅读、目录、代码 | Grid、Lightbox、EXIF |
| 数据模型 | Post/Tag | Gallery/GalleryImage |
| 隐私要求 | 文章内容 | GPS、EXIF、原图保护 |
| Cloudinary 目录 | 普通媒体 | 独立 Gallery folder |

因此，Gallery 最终被拆为独立领域，而不是通过 `layout: gallery` 混入 Post。

这是整个路线中比较成功的架构判断。

## 2. Gallery 建设过程

Gallery 大致经历了：

1. 前端硬编码原型；
2. `album.yaml` 和 `gallery.yaml` 内容规范；
3. `Gallery` / `GalleryImage` 数据模型；
4. WebP 预处理；
5. EXIF 白名单；
6. Cloudinary 独立目录；
7. `/gallery` 和 `/gallery/[slug]`；
8. 响应式 Grid 和 Lightbox；
9. Dashboard 管理；
10. revision、hash、merge base 和冲突处理；
11. 图片级评论；
12. Gallery 标签、缩略图和信息面板。

## 3. 这一阶段的经验

### 经验十：独立内容域应拥有独立人工源和数据模型

不要因为多个内容都“可以展示成卡片”，就强行共享同一个数据模型。

正确的共享方式是：

```text
共享基础设施
不共享领域语义
```

例如可以共享：

- 权限；
- 日志；
- 图片上传底层能力；
- 发布锁；
- 错误处理；
- DTO 工具；

但不应共享：

- Post 和 Gallery 的业务字段；
- 内容解析规则；
- 删除状态语义；
- 人工内容源；
- 前台查询模型。

### 经验十一：媒体处理应区分原始输入、处理结果和 CDN

最终形成了比较清晰的媒体边界：

```text
原始图片
  → .gallery-input/，不提交 Git
  → 本地处理为 WebP
  → WebP 进入 Git
  → 同一份 WebP 上传 Cloudinary
  → 数据库保存运行时 URL 和元数据
```

这比直接将 Cloudinary 当成原始图片来源更可靠。

但必须明确：

> 原始图片不在 Git、数据库快照或 Cloudinary 中时，用户必须自行承担额外备份责任。

# 六、大阶段五：同步体系平台化与复杂度增长

## 1. 阶段目标

Stage 7 和 Stage 8 试图将 Post 与 Gallery 的流程平台化，提供：

- 统一同步入口；
- `posts` / `galleries` / `all` scope；
- `runId`；
- `SyncRun`；
- TTL 锁；
- 运行摘要；
- 部分成功；
- scope 级 retry；
- Dashboard 同步中心；
- 三方冲突；
- `mergeBase`；
- `revision`；
- `PENDING_DELETE`；
- Gallery patch 和回写；
- 数据库运行记录。

## 2. 这套设计解决了什么

对于单管理员项目，它确实解决了一些真实问题：

- 同步运行是否卡死；
- CLI 和 Dashboard 是否重复触发；
- Post 和 Gallery 各自处理了什么；
- 同步失败后如何再次运行；
- Gallery 删除是否需要确认；
- 不同领域是否可以独立失败；
- 运行结果是否可查询。

TTL 运行保护是一个相对适合个人项目的轻量方案：

```text
运行开始 → 记录运行状态和过期时间
异常退出 → TTL 到期后允许恢复
重复触发 → 返回 LOCKED
不引入队列、不排队
```

## 3. 复杂度是如何累积的

随着功能增加，系统逐渐出现：

- `sync` 与 `publish` 多套命名；
- Post 和 Gallery 各自的同步入口；
- 数据库到文件回写；
- Dashboard 内容编辑；
- 数据库文章导出；
- 三方 merge；
- conflict 状态；
- revision；
- merge base；
- `retryOf`；
- `SyncRun`；
- TTL 锁；
- Snapshot；
- Cloudinary 删除状态；
- 多个 CI workflow；
- 多个兼容 DTO。

此时系统已经越来越像：

```text
Git ↔ Database ↔ Dashboard ↔ Cloudinary
```

而不再只是：

```text
编辑内容 → 发布网站
```

## 4. 这一阶段的经验

### 经验十二：统一入口不等于统一领域

Stage 8 中“统一入口、独立领域”的方向是正确的：

```text
统一：
- scope
- runId
- summary
- lock
- error code
- Dashboard 触发

不统一：
- Post / Gallery 数据模型
- 人工源
- 媒体处理规则
- 内容字段
- 删除语义
```

未来其他项目也可以采用类似方法，但需要警惕“公共编排层”逐渐吞噬领域逻辑。

### 经验十三：不要过早实现完整双向同步

双向同步不是简单地增加一个 `pull` 命令，它会自然引入：

```text
谁是真相？
    ↓
revision
    ↓
merge base
    ↓
hash
    ↓
conflict
    ↓
retry
    ↓
patch
    ↓
write-back
    ↓
审计和恢复
```

如果项目没有多人协作、多个编辑入口或明确的数据库内容编辑需求，双向同步通常不值得一开始就实现。

### 经验十四：复杂度必须有对应的业务频率

以下能力都可能有价值，但不一定适合个人博客：

- 实体级 retry；
- 任务队列；
- 多环境审批；
- 完整审计；
- 数据库文章导出；
- 在线内容编辑器；
- 三方 merge；
- 自动 Cloudinary 回收；
- 完整站点快照。

应始终问：

```text
这个问题多久发生一次？
人工处理需要多少分钟？
自动化系统需要维护多少年？
```

如果人工处理成本很低，复杂自动化可能得不偿失。

# 七、大阶段六：内容生产闭环、快照与治理

## 1. Stage 9 的方向

Stage 9 试图将系统整理成一条完整的内容生产闭环：

```text
编辑 Markdown / album.yaml / 原始图片
        ↓
content:check
        ↓
content:format / gallery:index / media prepare
        ↓
git diff 审查
        ↓
sync dry-run
        ↓
提交 Git
        ↓
正式同步
        ↓
数据库运行时副本
        ↓
Blog / Gallery
```

同时增加：

- `content:verify`；
- `content:prepare`；
- Dashboard 数据库快照；
- PRE_RESTORE 保护快照；
- Schema 字段审计；
- 文档治理；
- 默认 `sync=ALL`；
- CI 质量门禁。

## 2. 快照的正确边界

快照只保护数据库业务副本：

```text
Post
Tag
Gallery
GalleryImage
SiteProfile
可选 Comment
```

明确排除：

```text
User
Session
Account
Verification
SyncRun
SyncLog
锁
Cloudinary 二进制
Git 内容源
原始图片
```

这项边界设计是正确的，因为数据库快照无法恢复：

- Markdown；
- `album.yaml`；
- WebP；
- Cloudinary 原图；
- Git 历史；
- 应用代码。

因此快照只能叫：

> 数据库业务副本快照

不能叫：

> 完整站点备份

## 3. 暴露出来的关键问题

Stage 9 之后的审计发现，项目虽然“形式上”建立了完整流程，但一些关键语义并没有真正落实：

### dry-run 不完全只读

旧实现中曾存在：

- dry-run 写回 Frontmatter；
- Gallery dry-run 创建目录；
- dry-run 获取数据库锁；
- dry-run 创建或更新 `SyncRun`；
- CI 依赖真实数据库和 Cloudinary。

这是非常重要的经验：

> “dry-run”不是一个命令行参数，而是一组必须被测试证明的副作用约束。

### 发布仍可能写入人工源

正式 publish 曾经可以：

- 自动补齐 Post Frontmatter；
- 写入 Gallery `album.yaml`；
- 创建 Gallery 目录；
- 处理未准备媒体；
- 执行隐式内容修复。

这直接违背 Git-first 的核心原则。

### CI 并不是真正的质量门禁

如果质量检查需要：

- 生产数据库；
- Cloudinary Secret；
- 可写运行记录；
- 生产锁；

那么 CI 仍然和运行时发布系统耦合，质量检查就不再是纯验证。

### 同步锁存在竞态

“先查询是否已有运行，再插入新运行”的设计可能存在：

```text
A 查询：没有运行
B 查询：没有运行
A 插入
B 插入
```

TTL 只能解决异常退出后的释放，不能单独解决并发竞争。

## 4. 这一阶段的经验

### 经验十五：必须区分质量门禁和真实发布

推荐拆成两层：

```text
quality check
  - lint
  - tsc
  - parser check
  - content check
  - pure dry-run
  - build
  - tests
  - 不连接生产数据库
  - 不上传 Cloudinary
  - 不创建运行记录

release publish
  - db:migrate
  - 受控 publish
  - Cloudinary
  - PostgreSQL
  - 运行记录
```

### 经验十六：恢复系统要同时考虑三种状态

任何恢复操作都必须同时说明：

```text
Git 内容源
数据库运行时副本
Cloudinary 媒体
```

恢复数据库之后，下一次发布可能重新覆盖恢复结果。因此恢复后的正确提示应是：

```text
数据库副本已恢复；
Git 内容源未回滚；
Cloudinary 未回滚；
下一次 publish 可能覆盖当前恢复结果。
```

### 经验十七：不要用文档声明替代验证

文档中写“dry-run 不写入”并不能证明它真的不写入。

应通过测试断言：

- 文件 hash 不变；
- 数据库写入函数未调用；
- Cloudinary 上传函数未调用；
- 锁函数未调用；
- 运行记录创建函数未调用；
- 目录未创建；
- `album.yaml` 未变更。

# 八、大阶段七：架构减法与 Git-first 回归

## 1. 转折点

Stage 9 之后，项目开始主动承认：

> 当前系统围绕“同步系统本身”建设了太多能力，已经超过个人博客真正需要的复杂度。

最终的架构判断是：

```text
Git 是唯一人工内容源
PostgreSQL 是运行时副本
Cloudinary 是媒体 CDN
Dashboard 是运行时管理和观察工具
Git 负责内容版本恢复
数据库备份负责数据库恢复
```

目标数据流重新收敛为：

```text
Markdown / album.yaml / WebP
        ↓
content check / media prepare
        ↓
Git commit
        ↓
publish
        ↓
PostgreSQL + Cloudinary
        ↓
Blog / Gallery
```

## 2. 明确废弃的复杂度

架构减法明确不再扩展或逐步删除：

- 数据库 → Markdown 回写；
- Dashboard 内容编辑；
- `sync:pull`；
- `gallery:pull`；
- 数据库文章导出；
- 三方 merge；
- `mergeBase`；
- `revision`；
- `syncVersion`；
- 实体级 retry；
- 自动 Git commit/push；
- 独立 Cloudinary 上传入口；
- 数据库快照作为内容恢复机制；
- 多套同步 workflow；
- Cloudinary 作为内容元数据来源。

## 3. 保留的能力

架构减法不是“把系统变回最简静态博客”，而是保留真正有价值的能力：

- Markdown 内容；
- Gallery；
- `album.yaml`；
- WebP 媒体处理；
- Sharp；
- EXIF 白名单；
- Cloudinary CDN；
- PostgreSQL 查询副本；
- 内容检查；
- 格式化；
- Gallery 索引；
- 单向幂等 publish；
- Dashboard 状态查看；
- 评论、用户和站点设置；
- 管理员权限；
- 数据库备份和必要的运行记录；
- `dry-run`；
- Publish Assistant/TUI。

## 4. 逐步简化的策略

没有选择一次性重写，而是采用：

```text
冻结新增复杂度
    ↓
禁用危险的反向能力
    ↓
让 publish 成为唯一正式入口
    ↓
修复 dry-run 副作用
    ↓
迁移调用方和 DTO
    ↓
拆分 Post/Gallery Publish Service
    ↓
删除无调用方 helper
    ↓
最终删除旧 Sync 核心
```

这是一个值得复用的架构治理方式。

## 5. 这一阶段的经验

### 经验十八：架构减法也需要路线图

“删除复杂度”并不等于直接删目录。正确顺序是：

```text
停止新增依赖
→ 找到所有调用方
→ 标记兼容边界
→ 迁移调用方
→ 建立新测试
→ 删除旧实现
→ 删除 schema 字段
→ 清理文档
```

### 经验十九：兼容层应该有明确的期限和退出条件

兼容入口可以暂时保留，但必须明确：

- 谁还在调用；
- 是否允许新代码依赖；
- 返回什么迁移提示；
- 何时删除；
- 删除前需要哪些测试和数据审计。

否则“兼容期”很容易变成永久维护负担。

### 经验二十：正式入口应该少而清晰

最终建议的正式流程是：

```bash
bun run content:check
bun run content:verify
bun run publish -- --scope all --dry-run
bun run publish -- --scope all
```

Gallery 的准备过程可以保持显式：

```bash
bun run content:prepare-media
bun run gallery:index
```

重点不是删除所有命令，而是：

> 让用户知道哪一个是正式入口，其他命令分别负责什么。

# 九、从这次路线中提炼出的核心经验

## 1. 个人项目最重要的是“可理解性”，不只是“能力完整”

系统可以支持：

- 双向同步；
- 冲突合并；
- 运行记录；
- 快照恢复；
- Dashboard 编辑；
- Cloudinary 管理；
- 自动删除；

但如果用户每天发布一篇文章需要理解十几个概念，系统就已经偏离目标。

应优先设计：

```text
低认知成本
低运维成本
可预测副作用
容易回滚
容易解释
```

## 2. 单向数据流应尽早确定

最稳定的内容架构通常是：

```text
人工源 → 校验 → 发布 → 运行时副本
```

而不是：

```text
Git ↔ 数据库 ↔ Dashboard ↔ CDN
```

双向编辑只有在以下条件同时存在时才值得实现：

- 多个真实编辑入口；
- 多人或多设备共同编辑；
- 数据库侧编辑具有明确业务价值；
- 冲突处理成本高于系统维护成本；
- 有足够的测试、审计和恢复能力。

## 3. “自动化”不应隐式改变用户内容

任何会修改以下内容的操作都应该是显式命令：

- Markdown；
- Frontmatter；
- `album.yaml`；
- `gallery.yaml`；
- WebP；
- Git 工作区。

推荐：

```text
自动检查 → 给出修复建议 → 用户明确执行 → 用户审查 diff → 再发布
```

不推荐：

```text
publish → 自动修复 → 自动生成 → 自动上传 → 用户事后发现 diff
```

## 4. dry-run 必须定义为副作用契约

一个真正的 dry-run 应满足：

```text
不写文件
不创建目录
不写数据库
不创建运行记录
不获取生产锁
不上传 Cloudinary
不删除媒体
不修改状态
```

如果需要“连接数据库模拟真实运行”，应使用另一个明确命名的模式，而不是把所有行为都塞进 `--dry-run`。

## 5. 删除是高风险操作，应与普通发布分离

内容源暂时缺失不等于用户确认删除。

可能导致误判的原因包括：

- Git 分支切换；
- 不完整 checkout；
- 临时重命名；
- 发布中断；
- 路径错误；
- `.gallery-input` 尚未处理；
- index 尚未重新生成。

因此推荐：

```text
发现缺失
  ↓
只报告或标记
  ↓
管理员查看影响范围
  ↓
明确确认
  ↓
独立删除流程
```

普通 publish 不应直接删除数据库内容或 Cloudinary 资源。

## 6. 内容恢复、数据库恢复和媒体恢复必须分开

三类数据需要三套恢复方式：

| 数据 | 恢复方式 |
|---|---|
| Markdown、YAML、WebP | Git revert、branch、tag、仓库备份 |
| PostgreSQL | Neon backup、pg_dump、受控恢复 |
| Cloudinary | 媒体保留策略、原始图片备份、CDN 资源恢复 |

任何“站点快照”都必须清楚说明自己覆盖了哪一层，避免让用户产生“已经完整备份”的错觉。

## 7. 文档治理本身就是架构治理

这次路线中一个反复出现的问题是：

- 代码已经变化；
- 旧计划仍被当作当前规范；
- README、AGENTS、Stage 总结互相矛盾；
- 历史命令看起来仍然可用；
- Agent 可能依据过时文档继续扩展已废弃能力。

因此，未来项目应明确区分：

```text
当前架构规范
当前开发计划
已完成总结
历史计划
讨论稿
审计报告
```

并建立单一的当前状态入口，例如：

```text
documents/project-status.md
documents/architecture/README.md
```

旧文档保留时必须标记：

```text
历史规划，不代表当前实现和正式操作流程
```

# 十、适用于未来项目的推荐规划方法

## 阶段 0：先写边界，而不是先列功能

在开始开发前先明确：

```text
人工内容源是什么？
运行时副本是什么？
媒体系统负责什么？
Dashboard 能不能编辑内容？
恢复边界是什么？
删除由谁确认？
哪些操作必须 dry-run？
```

如果这些问题没有答案，不宜直接开始实现同步和后台编辑。

## 阶段 1：先完成单向最小闭环

推荐最初只实现：

```text
内容文件
  ↓
校验
  ↓
构建/媒体处理
  ↓
发布
  ↓
运行时查询
```

同时确保：

- 可重复执行；
- 不改变人工源；
- 失败可以重跑；
- 输出清晰摘要；
- 可以通过 Git 回滚。

## 阶段 2：根据真实痛点增加运维能力

只有当真实遇到问题时再加入：

- 运行记录；
- 锁；
- Dashboard；
- 快照；
- 删除确认；
- 失败重试。

每引入一个能力，都问：

```text
它解决了哪个真实问题？
它增加了哪些状态和长期维护成本？
能否通过更简单的人工流程解决？
```

## 阶段 3：先建立测试，再扩展复杂度

核心边界至少应该有测试：

```text
content check
publish dry-run
source immutability
permission
delete confirmation
lock
snapshot restore
partial failure
```

没有这些测试，不应声称：

- 支持安全删除；
- 支持可恢复同步；
- 支持完整快照；
- 支持并发保护；
- 支持真正只读 dry-run。

## 阶段 4：设置复杂度预算

可以为项目明确设定约束：

```text
不引入队列
不引入 Redis
不支持实体级 retry
不支持数据库到内容源回写
不允许第二套内容编辑入口
不允许独立媒体发布入口
```

如果未来确实需要突破限制，必须说明：

- 具体业务需求；
- 当前方案为什么不够；
- 新复杂度的维护成本；
- 迁移和回滚方案。

# 十一、最终总结

这次开发路线最重要的价值，不只是完成了博客、Gallery、评论、Dashboard 和发布能力，而是通过实际演进验证了一个架构判断：

> **个人博客最需要的不是功能最多，而是内容源明确、发布过程可预测、失败容易恢复、日常使用足够简单。**

整个项目最终从：

```text
博客 + Gallery + Dashboard + Git + Database + Cloudinary
+ 双向同步 + 冲突合并 + 快照 + 多套 workflow
```

重新收敛为：

```text
Git 内容源
    ↓
检查与媒体准备
    ↓
单向 Publish
    ↓
PostgreSQL 运行时副本
    ↓
Cloudinary CDN
    ↓
Blog / Gallery
```

最值得保留的经验可以浓缩为以下十条：

1. 先统一核心领域模型，再扩展产品功能。
2. 独立内容域应拥有独立人工源和数据模型。
3. Git-first 项目不要轻易引入双向同步。
4. Dashboard 默认应是运行时管理工具，不是第二个内容编辑器。
5. 所有会修改人工源的行为都必须显式、可审查。
6. dry-run 必须通过自动化测试证明真正只读。
7. 删除、回写和媒体清理必须独立于普通发布。
8. 快照、Git 回滚、数据库恢复和媒体恢复必须明确区分。
9. 兼容层必须有迁移计划和删除条件。
10. 当架构复杂度开始超过业务规模时，最有价值的工作可能是删除功能，而不是继续增加功能。
