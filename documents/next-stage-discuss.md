## 总体判断

这些想法可以组成一个完整的“本地内容工作台”，但我建议先把它限定为：**管理本地 Git 内容、帮助检查和发布；不把它做成另一套数据库内容编辑器。**

这与项目当前的单向数据流并不冲突：

```text
本地工作台 → Git 管理的 Markdown / YAML / 图片
             ↓
        校验、媒体准备
             ↓
          Publish
             ↓
      PostgreSQL / Cloudinary
```

本轮仅调研和分析，**没有修改文件**。

## 与现有实现的关系

- 当前内容源是 Git 管理的 Post、Gallery 配置和处理后的 WebP；数据库是运行时副本。项目文档明确不希望 Dashboard 成为第二个内容编辑器。
- 现有 `publish:tui` 已能执行内容检查、查看 Git 状态和 diff、dry-run，并在确认后真实发布。它是命令行维护助手，并不做自动 Git 提交或推送。
- Gallery 原图目前有专门的导入位置 `content/.gallery-input/`，处理后生成 WebP 并写入相册目录。现有命令已覆盖媒体准备、相册索引、内容校验和发布的主要步骤。
- GitHub Actions 当前暂停；因此“Git 推送”和“发布到网站数据库/CDN”是两件独立的事，不能假设 push 会自动完成 publish。
- Dashboard 删除并不等于从内容源删除：当前 Post 删除入口会阻止数据库物理删除；另有需要预览和确认的删除流程，但主要执行归档或标记待删除。Publish 对 source missing 只报告，不会因文件消失就自动删除数据库数据。

## 分项分析与建议

### 1. 本地图形内容工作台：可行，建议与线上 Dashboard 分工

建议把它定位为**本地内容工作台**，而不是把线上 Dashboard 搬到本机：

| 功能 | 建议由谁负责 |
|---|---|
| 导入文件、整理内容目录、修改 Markdown/YAML、查看本地 Git diff | 本地工作台 |
| 用户、评论、运行状态和线上运维观察 | Dashboard 或受保护的查询接口 |
| 发布和 Cloudinary 上传 | 继续复用统一 Publish Workflow |

图形界面的实现可以先考虑本地 Web UI，而不急于引入 Electron/Tauri。项目已使用 Next.js、React 和现有 UI 组件，Web UI 可以复用这些能力；对于选取文件夹，可以通过文件选择/上传流程导入，而不是让浏览器获得任意访问电脑文件系统的权限。若以后确实需要系统级文件浏览、桌面通知等能力，再评估桌面壳。

本地界面涉及本地文件、Git 和数据库凭据，安全边界仍然重要：服务应只监听本机地址，限制可操作的项目根目录，拒绝路径穿越与不可信符号链接，并且不能把 `.env` 中的凭据返回给浏览器。提交、推送、publish 等有副作用的步骤应分别展示结果并单独确认，不要做成一个无法中止的“全自动黑盒”。

### 2. 内容导入与整理：复用现有处理流程，不另造一套发布逻辑

**Post 导入**可引导用户选择 Markdown 和图片，预览解析结果，再生成项目认可的目录结构和 Frontmatter。界面可以先编辑常用字段，如标题、slug、日期、标签、摘要和封面；正文继续使用现有编辑器，避免第一阶段就开发完整 Markdown 编辑器。

**Gallery 导入**应保留现有边界：原图进入忽略 Git 的输入目录，处理后生成 WebP，`album.yaml` 是人工配置源，`gallery.yaml` 由索引命令生成。界面应调用现有媒体准备、Gallery 索引和检查逻辑，不能产生另一份与 CLI 不同的实现。

验收重点应包括：默认不覆盖现有文件；操作前显示将新增、修改和移动的文件；生成文件与手动编辑文件明确区分；完成后能查看 Git diff。

### 3. 评论辅助决策与删除：需要把“归档”和“永久删除”分开

数据库已有 Post 评论和 Gallery 图片评论。Post 删除 Post 记录时，外键会级联删除评论；Gallery 图片评论也有类似级联关系。删除预览目前可以统计关联评论，并显示媒体来源，但“统计评论”不等于已有安全的内容文件删除与数据库清理闭环。

尤其需要注意：Publish 不会因为某个源文件缺失就自动删除数据库记录。因此，不应把“把文件移出 `/content`”和“清掉文章及回复”当成一次普通 Publish 操作。

建议的生命周期是：

1. **先归档或隐藏**：这是可恢复的软操作，不删除评论。
2. **再预览永久删除影响**：展示文章、回复数量、Gallery 图片与媒体影响。
3. **显式确认后分别处理**：本地源文件进入备份；数据库数据采用单独、可审计的删除流程；Cloudinary 是否删除也须单独确认。
4. **支持恢复说明**：明确 Git 历史、数据库备份、Cloudinary 媒体备份分别保护什么。

如果需要额外本地备份，可以考虑 Git 忽略的项目根目录备份区，例如 `.local-backups/content/`，保留相对目录结构并用时间戳避免重名。但这只是本机上的额外保险，不能替代 Git 历史；也不宜把备份放进会被内容扫描和发布的 `content/` 内。

评论列表应优先提供必要的决策信息，如回复数、最近回复或评论概况，并遵守现有公开 DTO 的隐私边界，避免把邮箱等不必要的个人信息带到本地界面。

### 4. Git 与发布全流程：整合操作可以，自动执行不建议

一键工作流适合提供**连续引导**，不适合把所有副作用绑成一个不可见的自动操作。推荐步骤为：

```text
导入 / 编辑
→ 内容检查与媒体准备
→ 查看变更和 Git diff
→ dry-run
→ 用户确认真实 Publish
→ 用户选择是否 stage / commit / push
```

或者按项目习惯先提交并推送，再执行真实 Publish。重点是明确先后策略：远端推送失败时是否允许发布？publish 成功但 push 失败时如何提示？由于 Actions 暂停，UI 不能把 push 成功显示成网站已更新。

尤其应避免默认执行 `git add .`、自动创建提交或自动推送；只对本工作流修改的内容路径展示可审查的 Git 操作。现有 `publish:tui` 的检查与 dry-run 引导可以作为第一阶段基础，但真实发布、Git 提交、Git 推送最好仍是不同的确认点。

### 5. Publish 接口与数据库结构：先稳定契约，不急于改表

当前已有 CLI、TUI 和 Dashboard 共用 `runPublishWorkflow()` 的方向。要支持更多维护入口，首先应稳定**内容输入格式、校验报告、发布摘要、错误结构和版本兼容约定**，而不是先把 PostgreSQL 表结构改成第三方直接依赖的接口。

建议区分三层：

- **人工内容格式**：Markdown Frontmatter、`album.yaml` 等；
- **Publish 契约**：输入范围、dry-run 语义、结果和错误码；
- **内部数据库模型**：属于实现细节，不直接等于对外 API。

这样未来的第三方维护工具可以调用明确的 Publish 接口或生成符合格式的内容，而不必直接写 Post、Gallery、Comment 等内部表。当前文档也特别建议先整理 Publish 职责、不要只为改名立刻迁移运行记录表；我赞成先做契约和测试，数据库迁移等确认真实兼容需求后再决定。

### 6. Short URL 和 Gallery 图片深链接：是两个相关但独立的需求

当前 Gallery 结构是：

- `/gallery`：浏览全部相册；
- `/gallery/[albumSlug]`：直接浏览指定相册；
- 选中的图片主要通过客户端状态和 `#image-{imageId}` 表示。

所以你的判断基本正确：需要的是**图片可寻址的长链接**，例如：

```text
/gallery/{albumSlug}/{imageKey}
```

这是规范内容路径，适合复制、搜索引擎和长期链接。`imageKey` 应尽量稳定：按当前数据库图片 ID 做会耦合随机数据库 ID；按显示序号做会因排序改变而失效；按文件名主干或显式稳定 slug 通常更合适，但要定义重复标题、文件改名和历史链接的处理规则。

Short URL 则是另一层分享入口，例如：

```text
/s/{code} → 重定向到规范的长链接
```

如果希望二维码长期有效，我倾向让 short code 独立于可变标题和路径，并在内容移动或重命名后仍可维护映射。二维码应该编码短链接；短链接入口通过服务端重定向到长链接，这样最终浏览器地址栏仍显示你希望的完整路径。当前项目没有二维码相关实现或依赖，实施时再选用生成方案即可。

Gallery 深链接和短链接建议先后实施：**先让每张图片有稳定规范长链接，再给文章与图片增加短码和二维码**。这样短链只是稳定的转发入口，不会反过来承担内容寻址职责。

## 建议的分阶段顺序

1. **先确定边界**：本地工作台管理哪些内容；Dashboard 保留哪些在线运维功能；归档、恢复、永久删除分别意味着什么。
2. **先改善现有维护体验**：梳理 `publish:tui` 能复用的校验、修复、diff、dry-run 和 Publish 能力，确保新入口共用同一工作流。
3. **做本地内容导入与整理**：先 Post 和 Gallery 导入、元数据编辑、检查结果与文件 diff，保持写入 Git 内容源。
4. **加入 Git 操作引导**：显示文件变更，提供明确的选定文件 stage、commit、push 确认；Publish 仍单独确认。
5. **设计删除闭环**：归档优先；永久删除需显示回复和媒体影响，并分别确认源文件、数据库和 CDN 操作。
6. **增加 Gallery 图片长链接**，再增加 short URL 与二维码。
7. **第三方维护需求明确后**，再定版 Publish 契约与兼容策略；不预先把内部数据库 schema 固化成对外契约。

## 最需要先讨论的两个决策

1. **“开放第三方数据维护”具体是指什么？**  
   是第三方工具协助维护 Git 内容，还是第三方服务直接维护 PostgreSQL？我建议优先支持前者，通过受版本控制的内容格式和 Publish 契约接入，避免数据库成为第二个人工内容源。

2. **删除文章时，期望立即删除回复，还是先归档并保留回复？**  
   我建议默认先归档；永久删除必须单独预览并确认，因为回复是数据库中的用户数据，Publish 本身不负责因源文件消失而清理它们。

---

明白了。你的重点不是重做 Publish，也不是把 Dashboard 搬到本机，而是把现在分散在多个命令和文件操作中的**本地内容准备过程做成可视化工作流**；内容确认后，由界面直接调用现有 Publish，并展示实际运行结果。

这会让需求更清晰，也更符合项目已有的单向架构。

## 建议的用户流程

```text
打开本地内容工作台
  ↓
选择 / 检查项目工作区
  ↓
导入 Post 或 Gallery 素材
  ↓
可视化整理 Frontmatter、相册和图片
  ↓
查看将生成或修改的文件
  ↓
内容检查与发布预览
  ↓
确认内容并执行真实 Publish
  ↓
查看发布过程与结果
```

界面承担的是**编排和展示**：把现有能力串起来、减少用户手动敲命令；内容格式、检查规则、媒体准备和 Publish 写入仍由当前项目的实现负责，不另做一套平行逻辑。

### 内容整理阶段

- Post 用表单管理常用 Frontmatter 字段，例如标题、slug、日期、状态、标签、摘要和封面；正文仍可用现有 Markdown 工具编辑。
- Gallery 用界面导入图片、整理相册目录和 `album.yaml`；处理后的 WebP、索引生成和原图隔离规则继续沿用现有流程。
- 修改前后展示明确的文件清单和 diff，并区分用户编辑内容与自动生成文件。这样用户能看清楚界面实际会写入哪些文件。

### 确认与发布阶段

用户确认内容后，界面直接调用现有的 `runPublishWorkflow()`。界面不重写发布步骤，不绕过现有校验、数据库写入、Cloudinary 上传、运行保护或错误汇总。

“发布情况”应展示真实状态，而不是假造进度。现有 Publish 已有运行记录和结果摘要；如果希望实时看到更细的阶段进度，可以再确认底层服务目前能否提供阶段事件，必要时补充进度回调或状态查询，但仍保持同一个 Publish Workflow。

## 两个容易混淆的状态

**本地内容 Publish 不等于 Git push。** Publish 使用的是当前工作区内容；发布成功表示运行时副本已更新，不表示内容已经提交、推送或有 Git 历史记录。

因此我建议：

- 用户确认后允许直接执行 Publish，避免 Git 操作成为必须的前置步骤；
- 在发布前提示哪些内容尚未提交；
- 提供 Git diff、提交和推送的可视化入口，但作为独立确认的步骤，不让 Publish 成功/失败与 Git push 状态混为一谈；
- 明确显示“运行时 Publish 成功，但本地内容尚未推送”这类状态。

GitHub Actions 当前暂停，所以尤其不能把“推送成功”显示成“网站 Publish 成功”。二者应有各自的结果状态。

## 本地界面的边界与安全

因为界面需要读写本地内容，最好将它作为**仅本机运行的内容工作台**，而不是把文件系统操作加入线上 Dashboard。工作台应限制在选定项目目录内，并确保服务仅在本机可访问；部署到线上时不开放本地文件浏览或写入能力。

线上 Dashboard 则继续负责运行时状态和权限管理。未来如需在本地工作台显示评论数量等信息，可以把它作为辅助决策数据读取；它不因此成为内容源，也不直接编辑数据库里的文章或相册。

## 推荐的第一阶段范围

先做一个能闭环的本地工作流：

1. 浏览并导入 Post、图片和 Gallery 素材；
2. 表单化编辑常用 Frontmatter 与相册配置；
3. 调用现有内容整理、媒体准备和检查能力；
4. 展示生成文件、Git 状态和 diff；
5. 用户确认后直接运行现有 Publish；
6. 展示 Publish 结果、错误和未完成的 Git 操作。

这样首先解决的是“用户需要知道并输入很多命令”的问题，而不是增加新的内容源、发布引擎或同步机制。短链接和 Gallery 图片长链接仍可独立排期，不必成为本地工作台首期的前置条件。
